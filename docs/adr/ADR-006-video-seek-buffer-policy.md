# ADR-006: 视频 seek 与缓冲策略

## 状态

Accepted (2026-05-28)

## 1. 概述 (Summary)

为提升 PixScroll 视频播放页的进度拖动响应，决定在 `VideoPlayerFactory` 中使用较短的 LoadControl 缓冲参数，并设置 `SeekParameters.CLOSEST_SYNC`。在 `VideoPlayerScreen` 中，Slider 拖动期间只更新 UI 临时值，不对播放器执行每帧 seek；用户松手后只根据最终值执行一次 seek。

该决策优先优化浏览/预览场景的响应速度与稳定性，不追求逐帧精确落点。

## 2. 背景 (Context)

视频播放页存在两类性能压力：

1. **seek 频率压力**：Slider 拖动会产生高频 `onValueChange`。如果每次变化都调用 `seekTo()`，播放器会反复寻找同步帧、解码、缓冲，并可能持续中断前一次 seek。
2. **缓冲等待压力**：默认或偏保守的缓冲参数可能让 seek 后等待较多数据，影响本地媒体快速预览体验。

已有事实与约束：

- `VideoPlayerFactory` 将使用较短缓冲和 `SeekParameters.CLOSEST_SYNC`。
- `VideoPlayerScreen` 保持拖动中只更新 UI，松手 seek 一次。
- PixScroll 的视频播放主要是本地媒体浏览，不是逐帧剪辑工具。

## 3. 决策驱动 (Decision Drivers)

- **拖动响应优先**：Slider 拖动时 UI 必须跟手，不应被播放器解码/缓冲节奏反写。
- **减少无意义 seek**：用户拖动过程中的中间位置通常不会停留，连续 seek 浪费解码资源。
- **本地浏览优先**：对本地视频预览，快速落到附近可播放位置比逐毫秒精确更重要。
- **状态简单可控**：一次拖动最多一次 seek，便于推理和测试。
- **保留未来扩展**：如未来需要精确截图或剪辑，可为该功能单独启用精确 seek。

## 4. 决策 (Decision)

### 4.1 LoadControl 使用较短缓冲

`VideoPlayerFactory` 使用较短的 LoadControl 缓冲参数，以减少播放器在 seek 后等待大量缓冲完成的时间。

参数语义包括：

| 参数 | 语义 | 优化方向 |
|------|------|----------|
| `minBufferMs` | 播放器尝试维持的最小缓冲时长 | 缩短以降低预加载压力 |
| `maxBufferMs` | 播放器允许的最大缓冲时长 | 缩短以避免本地预览中过度缓冲 |
| `bufferForPlaybackMs` | 初次开始播放所需缓冲 | 缩短以更快开始播放 |
| `bufferForPlaybackAfterRebufferMs` | rebuffer 后恢复播放所需缓冲 | 缩短以更快恢复 |

具体数值以代码实现为准；维护时应基于真机验证调整，而不是凭主观感觉无限缩短。

### 4.2 使用 `SeekParameters.CLOSEST_SYNC`

seek 策略设置为：

```text
SeekParameters.CLOSEST_SYNC
```

含义：播放器可落到距离目标时间最近的同步帧。

取舍：

- 优点：通常比精确 seek 更快，减少为到达非关键帧而额外解码的成本。
- 缺点：实际落点可能与目标时间有小幅偏差，偏差大小取决于视频关键帧间隔和容器特性。

该策略适合：

- 本地视频快速浏览。
- 用户通过 Slider 粗略跳转到某个时间段。
- 预览而非编辑场景。

不适合：

- 精确截图。
- 逐帧剪辑。
- 需要毫秒级落点保证的功能。

### 4.3 Slider 不做每帧 seek

`VideoPlayerScreen` 的 Slider 行为固定为：

```text
onValueChange:
  - 标记正在拖动
  - 更新 UI 临时进度
  - 不调用 player.seekTo()

onValueChangeFinished:
  - 将最终 Slider 值转换为目标播放时间
  - 调用一次 player.seekTo(targetMs)
  - 释放拖动锁
```

拖动中播放器 position tick 不应覆盖 Slider 临时值；拖动结束后恢复由播放器 position 驱动 UI。

## 5. 为什么 Slider 不做每帧 seek

### 5.1 每帧 seek 的问题

每帧 seek 会产生以下问题：

1. **请求堆叠或互相取消**：新的 seek 很快到来，前一个 seek 还未完成。
2. **关键帧查找重复**：播放器持续查找同步帧，实际展示帧可能一直不稳定。
3. **UI 反写冲突**：播放器 currentPosition 与用户手指位置竞争 Slider 显示值。
4. **电量与发热压力**：高频解码和 I/O 对移动设备不友好。
5. **体验收益有限**：用户拖动中大多数中间位置不会被真正观看。

### 5.2 松手一次 seek 的收益

松手一次 seek 的行为更可控：

- 一次用户意图对应一次播放器动作。
- UI 拖动完全跟手，不等待播放器。
- seek 完成后再由播放器状态校正最终进度。
- 更容易记录和验证：一次拖动应只产生一次 seek。

### 5.3 为什么不使用简单节流替代

节流可以减少 seek 次数，但仍会在拖动期间触发多个 seek，且需要选择节流间隔。间隔过短仍有压力，间隔过长又表现为随机跳动。对于当前浏览场景，“拖动中不 seek，松手 seek 一次”更简单、稳定且符合用户最终意图。

## 6. 边界处理

实现与维护时需覆盖以下边界：

- `duration <= 0` 或未知时，不应计算非法比例或调用无意义 seek。
- 播放器未 ready 时，Slider 可显示占位或禁用拖动，不能崩溃。
- targetMs 应限制在 `[0, duration]` 范围内。
- 拖动取消、页面离开、播放器释放时，应清理拖动锁，避免 UI 卡在临时值。
- 横竖屏切换或生命周期恢复后，应以播放器当前状态恢复 UI。
- seek 失败或媒体异常时，应显示可降级状态，而不是继续反复 seek。

## 7. 备选方案 (Alternatives Considered)

### 7.1 每次 `onValueChange` 都 seek

优点：理论上拖动时画面可尝试同步预览。

缺点：

- 高频 seek 对播放器压力大。
- 容易出现 UI 回弹、卡顿和 seek 互相取消。
- 对本地浏览场景收益有限。

结论：不采用。

### 7.2 Slider seek 节流

优点：能减少 seek 次数，同时拖动中偶尔更新画面。

缺点：

- 节流间隔难以兼顾不同设备和素材。
- 仍然存在拖动中播放器 position 与 UI 临时值竞争。
- 实现复杂度高于当前收益。

结论：暂不采用；如未来需要拖动预览，可作为独立功能设计。

### 7.3 精确 seek

优点：落点更接近目标时间。

缺点：

- 可能需要额外解码非同步帧，响应更慢。
- 对当前浏览场景不是核心需求。

结论：不作为默认策略；未来精确截图/剪辑功能可单独启用。

### 7.4 保持播放器默认缓冲参数

优点：行为保守，适合更广泛媒体来源。

缺点：

- 本地预览 seek 后可能等待过多缓冲。
- 无法针对 PixScroll 的本地浏览场景优化。

结论：默认采用较短缓冲，但保留回滚能力。

## 8. 影响 (Consequences)

### 8.1 正向影响

- 拖动期间 UI 更稳定，避免每帧 seek 造成的卡顿和跳动。
- seek 次数显著减少：一次拖动对应一次最终 seek。
- `CLOSEST_SYNC` 有利于快速跳到附近可播放同步帧。
- 较短缓冲更符合本地视频快速浏览场景。

### 8.2 负向影响 / 成本

- 松手后的实际画面可能不精确落在目标毫秒。
- 高码率、慢存储、网络 URI 或特殊容器可能需要更保守缓冲。
- 如果用户期望拖动时实时画面预览，当前策略不会满足该需求。
- 需要真机验证不同 Android 版本、设备性能和视频编码组合。

## 9. 测试要求

### 9.1 功能验证

- 拖动 Slider 时，UI 临时进度跟随手指。
- 拖动期间不连续调用 seek。
- 松手后只调用一次 seek。
- seek 后 UI 最终回到播放器实际 position。
- duration 未知或 0 时无崩溃。
- 旋转屏幕、返回再进入、后台恢复后状态正常。

### 9.2 体验验证

记录以下信息，不写未验证绝对性能数字：

| 项目 | 记录 |
|------|------|
| 设备型号 / Android API |  |
| 视频格式 / 编码 / 分辨率 / 文件大小 |  |

| 松手后画面稳定主观耗时 |  |
| 实际落点偏差是否可接受 |  |
| 是否出现 rebuffer 或黑屏 |  |
| 是否需要调整缓冲参数 |  |

### 9.3 回归验证

- 普通播放、暂停、继续播放正常。
- 点击返回释放播放器，不泄漏播放声音。
- 从媒体网格进入视频、返回网格、再次进入均正常。
- 损坏视频或不支持格式可安全失败。

## 10. 回滚策略

如果真机验证发现体验变差，按以下顺序回滚：

1. 保留 Slider “拖动中不 seek，松手 seek 一次”的策略。
2. 将 LoadControl 缓冲参数调回更保守值或默认值。
3. 将 `SeekParameters.CLOSEST_SYNC` 恢复为默认 seek 参数。
4. 如确需拖动中预览，新增明确的预览模式并加节流，不直接恢复每帧 seek。
